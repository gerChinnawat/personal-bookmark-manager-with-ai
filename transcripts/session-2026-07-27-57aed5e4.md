### ASSISTANT (2026-07-27T06:24:38.522Z)

Can't reconstruct the exact origin now since the process (PID 88987) is already killed and macOS doesn't retain that history — but here's why this happens in general:

**Why a stray node process is running on 3000**

VS Code's integrated terminal doesn't always kill child processes when you close a tab. If you ran `npm run start:dev` (Nest's watch mode) and then closed the terminal tab, ended the debug session, or the VS Code window crashed/reloaded, the underlying `node` process can survive as an orphan — it just gets reparented to `launchd` instead of being torn down. Same thing can happen if you started it in a plain Terminal.app/iTerm window outside VS Code entirely.

**Why VS Code can't show it to you**

The Terminal panel only lists shell sessions VS Code currently owns and has a tab open for. An orphaned background process has no terminal tab attached anymore, so it's invisible there regardless of who launched it originally — VS Code has no general "here's every process on your machine" view (that's what Activity Monitor / `lsof` / `ps` are for).

**How to avoid it going forward**

- Always stop the dev server with `Ctrl+C` in its terminal rather than just closing the tab/window.
- If a port ever seems stuck, check with `lsof -nP -iTCP:3000 -sTCP:LISTEN` (what I used) — it'll show you the real PID even though VS Code can't.
- If you use the built-in JS Debug Terminal or a launch config, stopping the debugger should kill the process tree; a plain integrated terminal doesn't guarantee that.

Nothing to fix in code here — just a leftover process from a previous run.
